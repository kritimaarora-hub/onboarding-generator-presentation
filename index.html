The Problem

Onboarding gets redesigned from scratch — again and again

When teams design onboarding flows independently, the same problems keep appearing across products.

🔁

The same information is collected multiple times across different flows

📋

Unnecessary fields are added upfront, creating friction early in the journey

🧩

Inconsistent interaction patterns confuse users switching between products

🤖

Missed opportunities for auto-fill — users type things that already exist in the system

⚖️

Compliance requirements handled differently across every flow

📐

Design decisions drift during implementation with no shared reference

🔂

Teams repeatedly solve problems that another product already solved

🧠

Design knowledge lives in scattered files, individual memories, and old Figma screens

What if onboarding design could learn from every onboarding flow we have already built?

The multi-agent pipeline

A team of specialized agents analyses the problem, proposes structure, defines interactions, reviews, and iterates — before producing the final flow.

Agents don't work in isolation. They share context through a common knowledge base and communicate through a message bus. The Optimization Agent can send feedback back to the Flow Architect, triggering a revision loop.

Each agent has a distinct role in the pipeline, with a specific question it is responsible for answering.

Step-by-Step

What happens after you submit a prompt

From problem statement to final onboarding recommendation — here's what the system does internally.

1

You describe the problem

Enter a problem statement via the web UI or CLI. The richer the context, the more relevant the generated flow.

User type Onboarding mode Government IDs Volume First value moment Constraints
2

Research Agent builds context

The Research Agent searches the shared knowledge base for precedents, patterns, guidelines, and insights relevant to the problem.

Problem Statement → Search Knowledge Base → Research Summary
3

Flow Architect proposes the structure

Research output is handed to the Flow Architect, which determines how the journey should be divided into stages and what belongs at each step.

Research Output → Stage Planning → Onboarding Structure
4

Interaction Agent defines the UI logic

The Interaction Agent evaluates how users should interact with each stage — choosing the right inputs, grouping fields, identifying auto-fill opportunities.

Flow Structure → UI + Interaction Logic → Screen Proposal
5

Optimization Agent reviews everything

The complete proposal is checked against the knowledge base. The agent identifies issues, flags unnecessary complexity, and can send feedback back to the Flow Architect.

Full Proposal → Review vs Guidelines → Issues Flagged
6

Feedback loop (up to 2 iterations)

If architectural issues are found, feedback is sent back to the Flow Architect. The flow is revised, interaction logic is regenerated, and optimization runs again.

Feedback → Flow Architect → Revise → Re-optimize
7

Final output is returned

A structured onboarding recommendation is delivered across four layers — Research, Flow, Interaction, and Optimization — saved as a timestamped JSON file.

📋 Research 🏗️ Flow 🖱️ Interaction ✅ Optimization
Feedback Loop

The system can revise itself

When the Optimization Agent finds issues, it doesn't just flag them — it triggers a revision cycle, up to two times, before returning the final result.

The Output

🔍

Relevant precedents, user patterns, constraints, known risks, and insights that shaped the recommendation

🏗️

Flow

The proposed onboarding stages, sequence, branching logic, and what information belongs where

🖱️

Input types, field groups, conditional logic, auto-fill opportunities, and verification states

✅

Issues found, improvements applied, and a final assessment of the flow quality against guidelines

Example Use Case

From requirement to reasoned recommendation

Here's what the system does differently compared to starting from scratch.

📋 The Requirement
"Design self-onboarding for 500 warehouse candidates per day. Candidates need Aadhaar verification, employment details, education details, and bank information."

A designer without this system would likely produce one long form. The system takes a different approach.

💡 What the System Identifies
Aadhaar data can reduce manual entry — auto-fill name and date of birth
Employment and education details may not need to block initial onboarding
High-volume onboarding requires minimising interaction time per user
Low-literacy users require simpler interaction patterns and shorter steps
Some information can be progressively collected after the first meaningful completion state
Design Philosophy
"Do not make every designer solve the same onboarding problem from zero."
📚

Learn from previous flows

Every documented flow becomes part of the institutional memory the system reasons from

🧩

Maintain consistency

Interaction patterns and design rules are applied uniformly across new flows

⚡

Catch issues early

Avoidable UX problems are identified before any design work begins

🔬

Evidence-grounded decisions

Every recommendation is backed by documented flows, patterns, and real insights

🔁

Reduce repetitive work

Solved problems stay solved and become part of the shared starting point

🎯

Preserve design intent

Design decisions are documented and reusable across teams and product areas
